# 分步提交设计

状态：设计草案，尚未实现。此方案描述后续实现需要满足的行为，不证明当前 Steam 或 CS2 接受某个目标值。

## 字段限制的解释

以本次实际读取的 schema 为准，同时验证类型、范围、`incrementonly`、保护、权限与可信服务器限制。只读、不可读取和未知类型字段不能进入提交队列。

Steam 文档把 `maxchange` 描述为相邻 `SetStat` 调用之间允许的最大变化量。因此，`maxchange=1` 不能被简化成“每轮 StoreStats 成功就能再增加 1，重复必定达到任意目标”。本地设置是否接受、存储是否接受、最终读回是否一致是三个不同的检查点。

对于本地定义允许尝试的目标，每轮暂以最新读到的值为起点计算步幅，步幅不超过已知约束。浮点字段必须按实际可表示精度计算，无法形成有效进展时停止。这个策略不绕过服务器限制，是否可重复推进必须经过真实小范围验证。

已核对的官方机制、回调结构和重试分类详见 [Steam 提交机制研究](./steam-submission-research.md)。

参考入口：[Steamworks ISteamUserStats](https://partner.steamgames.com/doc/api/ISteamUserStats) 与 [Stats and Achievements](https://partner.steamgames.com/doc/features/achievements)。实现时需再核对当前文档和上游实际接口行为。

## 状态机

1. **预检**：确认游戏与账户上下文未变化、目标合法且没有其他未确认写入；显示变更、预计轮数、时长与停止含义，等待用户显式开始。
2. **读取当前值**：请求并等待最新统计数据回调，取得本轮基线。不能用界面上的旧缓存替代。
3. **计算本轮目标**：对未完成字段计算在当前限制内可尝试的下一值；已经到达目标的不再写入。无法推进则停止并指出具体字段。
4. **设置本地值**：调用字段对应的 `SetStat`，检查返回值。任一失败不得继续假定整批成功；应清理或重新读取可能已修改的本地缓存后停止。
5. **请求存储**：调用 `StoreStats`。返回 `true` 仅说明请求发起，不显示“已成功”。同一时间只允许一个待确认提交。
6. **等待存储回调**：处理 `UserStatsStored` 并核对游戏等可用上下文；按错误类型进入读回与有限退避、暂停或不确定状态；超时不直接重发。迟到与重复回调不得错误触发下一轮。
7. **重新请求与读回**：等待新的读取回调，比较实际值与本轮预期、上轮基线和最终目标。值无变化、被修正为其他值或出现外部修改时先暂停核验原因；可合法恢复的临时错误按读回值重新规划，重复拒绝则停止。不以本地缓存宣称服务器持久化成功。
8. **完成或等待**：所有目标达到时结束；否则进入分钟级等待，倒计时结束后从重新读取开始下一轮。

即使客户端回调与重新读取都符合预期，也只能报告实际观察到的证据，不保证游戏服务器今后不会覆盖。如何确认读取数据的刷新与持久性需在真实客户端验证中检查。

## 提交间隔与估算

暂以 120 秒作为设计建议起点。当前官方文档已确认建议分钟级调用，具体行为仍需后续 Windows 实测。这不是 Steam 公布的最快速度或固定限制，可保证的最短成功间隔目前未知。计划采用分钟级间隔，避免毫秒级重试或并行灌入请求；保守间隔也不能保证消除限流。

若某字段从当前值 `c` 到目标值 `t` 的差值为 `d = abs(t - c)`，且每轮可推进的有效步幅为 `s > 0`，粗略轮数为 `ceil(d / s)`。多字段同轮提交时，初步取所需轮数的最大值；实际会受字段校验与读回结果影响。

例如实际差值为 1,000、每轮可推进 1，才有至少 1,000 轮的估算。若采用 120 秒间隔，轮间等待约为 `(1000 - 1) × 120` 秒，即约 33.3 小时，另外还要加上各轮请求、回调和读取耗时。不能仅凭目标值本身估算，也不能把估算当作完成承诺。

## 自适应间隔与读回重规划

官方接口证据见上述研究文档；以下调度参数与恢复行为仍需后续实测确认，不能把任意失败都当成请求过快。

| 观察 | 计划处理 |
| --- | --- |
| 本地 `SetStat` 拒绝 | 核查字段类型、实际约束和本地读取状态；不靠缩短间隔重试 |
| 存储回调明确失败 | 保留实际错误码；区分参数、权限、连接和服务错误，再决定是否允许有限退避 |
| 回调超时 | 请求结果不明，不立即叠加下一次写入；先重建可靠读取状态 |
| 读回值与计划不同 | 记录实际值，不把计划值当成已接受值；重新校验目标和约束，再决定重规划或停止 |
| 已核实的暂时性错误或限流 | 若接口提供可信信息则遵循；否则采用有上限的保守退避，不声称知道服务器剩余额度 |
| 连续成功 | 只能说明当前环境下观察成功；若以后提供有限调整，也不能承诺探得长期有效的最快间隔 |

官方回调结构不包含逐字段当前值或建议等待时间。应通过有效的重新读取流程取得实际值，不能根据错误码推算。基于实际值重新加到下一步是合理候选，但必须在有效读取、字段仍可写、未出现外部冲突的前提下执行。

“延时重试以探测最快间隔”最多产生某个账户、游戏和时间段的观测结果。服务限流可能动态变化，成功一次不是稳定阈值；不计划主动高速失败探测。自适应功能应以可靠完成与减少无效请求为目标，设置调整边界、失败次数上限和清晰日志。

## 停止、失败与恢复

- “停止”阻止新的设置与后续轮次。等待期间应立即结束倒计时；提交已经发出时仍要处理回调并读取结果，再说明最终观察值。
- 停止不撤回已经发送的请求，不回滚已经写入的字段。原始导出文件仅作参考，受只增或服务器规则约束时可能无法恢复。
- 请求被拒绝、回调错误、超时、断线、无进展和读回不一致均应暂停或停止，并显示原因。不无限重试；按官方机制研究中提出的分类设计有限退避，具体阈值需实现前确定。
- 日志记录时间、阶段、字段 ID、本轮值、目标值、返回/回调结果与读回结果。日志保存在本机，用户主动导出才生成文件，不自动提交仓库。
- 初期不设计后台服务或系统自动启动。程序重启后重新读取最新数据，再导入用户保存的目标文件，经过预览和显式开始继续。

## 交互与验收要点

预览应清楚区分可单次尝试、需要分步和不可写的字段。运行时禁用会改变批次的导入、编辑及普通提交操作，避免把成就或其他未预览变化混入存储；“停止”和“日志”保持可用。

状态机须通过离线模拟验证失败、超时、迟到回调、重复回调、停止与无进展等情形。真实 Steam 小范围测试必须在实现后展示具体字段和目标，由用户确认后执行。当前方案尚未经过 Windows 构建、界面或真实 Steam 提交验证。
